1. High-Level Overview

The AutoRepair GUI is a WPF (Windows Presentation Foundation) desktop application that provides a visual front-end for the AutoRepair pipeline. Rather than running PowerShell scripts manually from the command line, users can:

  1. Drag & drop (or browse to) a C# project folder.
  2. Click ▶ Run Pipeline to execute all three pipeline steps automatically.
  3. Review generated patches in a visual diff-card interface.
  4. Apply or Reject patches with a single click, with full test verification.

4.3 Step Indicator Cards

Three step cards are laid out in a UniformGrid with Columns="3". Each card is a Border containing a status icon (○ / ⏳ / ✔ / ✘) and a status label ("Waiting" / "Running…" / "Complete" / "Failed"). The code-behind updates these dynamically by changing their Text, Foreground, and BorderBrush.

4.4 The TabControl — Log & Patch Review

The main content area uses a TabControl with custom-styled tab headers (rounded top corners, colour change on selection):

  • 📋 Output Log — A read-only TextBox inside a ScrollViewer, displaying real-time output from the pipeline processes.
  • 🔍 Patch Review — An ItemsControl bound to a list of PatchDisplayItem objects. Each patch renders as a card showing the file name, line number, rule, description, and a colour-coded original/patched diff.

4.5 Patch Diff Cards (DataTemplate)

The patch review tab uses a DataTemplate to render each patch as a visual card. This is a key XAML technique — each PatchDisplayItem object is automatically rendered into a styled card: 

<DataTemplate>

Design choice: Using WPF data binding and DataTemplate means the UI automatically generates one card per patch — no manual loop code needed. Just set PatchList.ItemsSource = patches; and WPF does the rest.

5. MainWindow Code-Behind

MainWindow.xaml.cs (~581 lines) handles all UI events and state management. It can be broken into five logical areas:

5.1 Drag & Drop / Browse Input

How project input works

The window has AllowDrop="True" with two event handlers:

  • Window_DragOver — highlights the drop zone border in blue when a valid file is dragged over.
  • Window_Drop — extracts the file path and calls AcceptPath().

Alternatively, clicking the drop zone opens a file dialog (DropZone_Click) for manual browsing.

5.2 Path Resolution & Project Detection

AcceptPath() → ResolveProjectLayout()

When a path is received (drop or browse), the code resolves the project structure:

  1. Determines if the path is a directory, .csproj, .sln, or another file.
  2. Calls ResolveProjectLayout() which scans for .csproj files in the folder and sub-folders.
  3. Separates source projects from test projects using IsTestProject().
  4. Auto-detects the test project via DetectTestProject() using naming conventions (*.Tests, *Test*) and NuGet package references (xUnit, NUnit, MSTest).

If no test project is found, the user is warned and can manually browse to one. The ▶ Run Pipeline button remains disabled until a test project is set. 

private static bool IsTestProject(string csprojPath)
{
    var name = Path.GetFileNameWithoutExtension(csprojPath);

    // Check naming convention
    if (name.EndsWith(".Tests") || name.EndsWith(".Test") || ...)
        return true;

    // Check for test framework NuGet references in the .csproj
    var content = File.ReadAllText(csprojPath);
    if (content.Contains("Microsoft.NET.Test.Sdk") ||
        content.Contains("xunit") || content.Contains("NUnit") || ...)
        return true;

    return false;
}

5.3 Pipeline Execution (BtnRun_Click)

The Run Pipeline button handler

When the user clicks ▶ Run Pipeline, the async handler:

  1. Disables buttons and resets all step indicators.
  2. Creates a CancellationTokenSource for cancellation support.
  3. Locates the AutoRepair root directory by walking up parent directories.
  4. Creates a PipelineRunner instance, wiring up its events:
    • OutputReceived → appends text to the log via Dispatcher.Invoke()
    • StepChanged → updates the step indicator cards
  5. Calls runner.RunAnalysisAsync() — the dry-run phase.
  6. On success, parses patches.json and populates the Patch Review tab.
  7. Shows the ✔ Apply and ✘ Reject buttons.

5.4 Patch Loading & Display

LoadPatches() and PatchDisplayItem

LoadPatches() reads the patches.json file generated by Step 3 and deserialises it into a list of PatchDisplayItem objects using System.Text.Json:

6. PipelineRunner — Process Orchestration

PipelineRunner.cs (~336 lines) is the engine that actually runs the pipeline. It has no UI dependencies — it communicates with the window purely through events.

6.1 Architecture

Clean separation of concerns
  • Two events are exposed:
    • OutputReceived — fires whenever a line of stdout/stderr is captured.
    • StepChanged — fires when a step transitions (Running / Success / Failed).
  • The runner holds a reference to the currently active Process so it can be killed on cancellation.
  • It caches the _violationsFile path from Step 2 so Step 3 (apply phase) can find it later.

6.2 Running PowerShell Processes

Each pipeline step is a PowerShell script. The runner launches them as child processes with System.Diagnostics.Process: 

private Task<int> RunPowerShellAsync(string arguments, CancellationToken ct)
{
    var psi = new ProcessStartInfo
    {
        FileName      = "powershell.exe",
        Arguments     = $"-NoProfile -ExecutionPolicy Bypass {arguments}",
        UseShellExecute      = false,
        RedirectStandardOutput = true,
        RedirectStandardError  = true,
        CreateNoWindow = true,
        WorkingDirectory = _autoRepairRoot,
    };
    return RunProcessAsync(psi, ct);
}
Key detail: The runner prepends the local .NET SDK path to the PATH environment variable. This ensures that the PowerShell scripts can find dotnet.exe even if it's installed in the per-user location rather than system-wide.

6.3 Real-Time Output Streaming

Output is streamed in real time using asynchronous line-by-line reading: 

private async Task<int> RunProcessAsync(ProcessStartInfo psi, CancellationToken ct)
{
    var process = new Process { StartInfo = psi, EnableRaisingEvents = true };
    var tcs = new TaskCompletionSource<int>();

    process.OutputDataReceived += (_, e) => {
        if (e.Data != null) Emit(e.Data + "\n");  // → fires OutputReceived event
    };
    process.Exited += (_, _) => { tcs.TrySetResult(process.ExitCode); };

    process.Start();
    process.BeginOutputReadLine();
    process.BeginErrorReadLine();

    // Cancellation kills the entire process tree
    using var reg = ct.Register(() => {
        process.Kill(entireProcessTree: true);
        tcs.TrySetCanceled(ct);
    });

    return await tcs.Task;
}

The TaskCompletionSource pattern bridges the event-based Process API into an async/await-friendly task. The method returns only when the process exits (or is cancelled).

7. Two-Phase Workflow (Dry-Run → Apply)

A critical design decision is the two-phase execution model. Rather than applying patches immediately, the pipeline runs in a "dry-run" first, then waits for user approval.

Phase 1 — Analysis (RunAnalysisAsync)

Steps 1 → 2 → 3 (dry-run)
  1. Pre-clean: Runs restore_project.ps1 to undo any leftover instrumentation from previous runs.
  2. Step 1 — Tracing: Runs generate_trace.ps1 with the source directory and test project as arguments. Produces trace_logs.jsonl.
  3. Step 2 — Constraints: Runs analyze_trace.ps1, which reads the trace logs and produces violations.json.
  4. Step 3 — Repair (dry-run): Runs generate_patches.ps1 without the -Apply flag, producing patches.json only.

Phase 2a — Apply (ApplyPatchesAndVerifyAsync)

User clicks ✔ Apply Patches
  1. Restore first: Runs restore_project.ps1 to get clean source files (removes any instrumentation artefacts).
  2. Apply: Re-runs generate_patches.ps1 with the -Apply flag, which modifies the actual source files.
  3. Verify: Runs dotnet test against the patched code to confirm the repairs pass all tests.
Why restore before applying? — Step 1 instruments the source files (adds tracing code). If patches were applied to the instrumented files and then a restore ran, the .bak files would overwrite the patches with the original code. So the flow is: restore → apply patches to clean originals → verify.

Phase 2b — Reject (RestoreSourceAsync)

If the user clicks ✘ Reject, the runner simply restores all .bak files, reverting the source to its original state with no patches applied.

9. Key Design Patterns & Techniques

🔧 Event-Based Decoupling

PipelineRunner has zero references to WPF classes. It communicates through OutputReceived and StepChanged events. The MainWindow subscribes to these and uses Dispatcher.Invoke() to marshal updates to the UI thread. This keeps the pipeline logic testable and UI-independent.

🔧 TaskCompletionSource for Process Lifecycle

The RunProcessAsync method wraps System.Diagnostics.Process (which is event-based) into an async Task<int> using TaskCompletionSource. This allows the caller to simply await process completion while still receiving real-time output via events.

🔧 CancellationToken Integration

Every async method accepts a CancellationToken. When the user clicks Cancel, the token is triggered, which registers a callback that kills the entire process tree (process.Kill(entireProcessTree: true)) and cancels the task.

🔧 WPF Data Binding + DataTemplate

The patch review UI uses WPF's data binding system. Each PatchDisplayItem is automatically rendered into a styled card via the XAML DataTemplate. No imperative UI code is needed to create or populate the cards — just PatchList.ItemsSource = patches;.

🔧 Smart Project Detection

The AcceptPath → ResolveProjectLayout → DetectTestProject chain uses a multi-strategy approach to find the test project: naming conventions first (e.g., sibling *.Tests directory), then falls back to scanning .csproj contents for test framework NuGet package references.

🔧 Catppuccin Mocha Theming via Resource Dictionaries

All colours are defined as named SolidColorBrush resources in Window.Resources. Changing the theme requires editing only the colour hex values in one place. The diff cards use distinct background colours — dark red (#2d1517) for original code and dark green (#152d1d) for patched code — mimicking a standard git diff view.
