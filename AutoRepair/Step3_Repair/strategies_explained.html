Section 1

How Strategies Work

Every repair in AutoRepair follows the same three-phase lifecycle: match, analyse, transform. The engine reads constraint violations from Step 2, then hands each violation to a chain of strategies. The first strategy that can handle it wins.

Constraint Violation
e.g. NotNull(dereference.receiver) at line 18 in Worker.cs
↓
Strategy 1: CanHandle()? → No → Strategy 2: CanHandle()? → No → ...
Strategies are tried in priority order (most specific first)
↓ Yes
TryRepair(violation, source, syntaxTree)
Roslyn parses the C# file → finds the AST node at the violation line → generates patch
↓
PatchResult
Original code, patched code, metadata → written to patches.json and optionally applied
Key idea: Each strategy is a specialist. OffByOneRepairStrategy only understands loop conditions. NullDereferenceRepairStrategy only understands null guards. The engine tries them in order and picks the first successful patch — this means more targeted fixes always win over generic ones.
Section 2

The Priority Chain

The 6 strategies are registered in a specific order. When multiple strategies could handle a violation, the one with the highest priority (lowest number) wins. This ensures the most precise fix is applied.

① OffByOne → ② BufferBounds → ③ NullDeref → ④ InvalidCast → ⑤ IntOverflow → ⑥ Exception

Why Order Matters — A Real Example

Consider a violation where an array access at items[i] crashes with both an OffByOne predicate (the loop runs one extra iteration) and a BufferInBounds predicate (the index is out of range):

Priority 1 wins — OffByOne
// Fixes the ROOT CAUSE: the loop condition
for (int i = 0; i < items.Length; i++)  // ← was <=
{
    Process(items[i]);
}

✓ Root cause fixed. Loop now iterates the correct number of times.

If Priority 2 ran instead — BufferBounds
// Only adds a guard — loop still runs too many times
for (int i = 0; i <= items.Length; i++)
{
    if (i >= 0 && i < items.Length) // ← extra guard
    {
        Process(items[i]);
    }
}

⚠ Symptom treated, but the extra iteration is still wasted.

Section 3

The IRepairStrategy Interface

Every strategy implements this two-method contract. It's simple by design — all the complexity lives inside each strategy's TryRepair implementation.

public interface IRepairStrategy
{
    /// Quick check: can this strategy handle the given violation?
    /// Usually just a string prefix match on the violation's Predicate field.
    bool CanHandle(ConstraintViolation violation);

    /// The heavy work: parse the AST, find the buggy node, generate a patch.
    /// Returns null if no actionable repair can be produced.
    PatchResult? TryRepair(
        ConstraintViolation violation,   // what's broken and where
        string sourceCode,               // the raw .cs file content
        CSharpSyntaxTree tree);         // Roslyn's parsed AST of the file
}
MethodCostWhat It Does
CanHandle() Cheap String prefix match on violation.Predicate. No Roslyn work. Called many times per violation.
TryRepair() Expensive Walks the Roslyn AST, finds specific syntax nodes, generates replacement code. Only called if CanHandle() returns true.
Design pattern: This is a classic Chain of Responsibility pattern. The engine iterates strategies in order, each one decides whether it can handle the violation. The first one that both CanHandle() returns true AND TryRepair() returns non-null wins. All subsequent strategies are skipped.
Strategy 1

OffByOneRepairStrategy

Fixes loops that iterate one element too far, causing array overflows

Priority 1 OffByOne(...)

When Does It Trigger?

The engine calls this strategy when a violation's predicate starts with "OffByOne(". This predicate is generated by Step 2 when it detects an array access at an index equal to the array's length (classic off-by-one).

What Does It Do?

It has two sub-strategies, tried in order:

Sub-Strategy A — Fix the Loop Condition
  1. Find all for and while loops in the file
  2. Check if the violation line falls inside one of these loops
  3. Inspect the loop condition for <= comparisons
  4. Rewrite <= → <
Best fix: Addresses the root cause. The loop now stops at the correct boundary.
Sub-Strategy B — Add Bounds Guard (Fallback)
  1. Find the statement at the violation line
  2. Locate array[index] expressions in it
  3. Wrap in if (index >= 0 && index < array.Length)
Fallback: Prevents the crash but doesn't fix why the loop runs too far. Used when no enclosing loop with <= is found.

Example A — Loop Condition Fix

Violation
"predicate": "OffByOne(buffer[i], index=5, length=5)"
"file":      "Worker.cs"
"line":      14
Worker.cs — loop condition changed from <= to <
  public void ProcessBuffer(int[] buffer)
  {
      for (int i = 0; i <= buffer.Length; i++)   // ← BUG: runs when i == 5
      for (int i = 0; i < buffer.Length; i++)    // ← FIXED: stops at i == 4
      {
          buffer[i] = i + 1;
      }
  }

Example B — Bounds Guard Fallback

When the loop can't be found or doesn't use <=:

Worker.cs — bounds guard added around array access
      buffer[i] = i + 1;
      if (i >= 0 && i < buffer.Length)
      {
          buffer[i] = i + 1;
      }

Roslyn Nodes Used

ForStatementSyntax WhileStatementSyntax BinaryExpressionSyntax (LessThanOrEqual) ElementAccessExpressionSyntax

Strategy 2

BufferBoundsRepairStrategy

Wraps array accesses in runtime bounds checks

Priority 2 BufferInBounds(...)

When Does It Trigger?

Fires for BufferInBounds(...) predicates — generic out-of-range array accesses that aren't specifically off-by-one loop errors.

Algorithm Step by Step

  1. Find the syntax node at the violation line using Roslyn's AST — picks the widest node starting at that line.
  2. Walk up to the enclosing statement — the full StatementSyntax that contains the violation.
  3. Find all ElementAccessExpressionSyntax nodes (these represent arr[i] patterns).
  4. Build a guard condition for each — index >= 0 && index < array.Length.
  5. Wrap the original statement inside if (guard) { ... }.

Example — Single Array Access

Violation
"predicate": "BufferInBounds(data[pos], index=10, length=8)"
"file":      "DataProcessor.cs"
"line":      42
DataProcessor.cs — bounds guard inserted
      result = data[pos];
      if (pos >= 0 && pos < data.Length)
      {
          result = data[pos];
      }

Example — Multiple Array Accesses in One Statement

When a statement accesses multiple arrays, all guards are combined:

Merger.cs — combined guard for two arrays
      output[k] = left[i] + right[j];
      if (k >= 0 && k < output.Length && i >= 0 && i < left.Length && j >= 0 && j < right.Length)
      {
          output[k] = left[i] + right[j];
      }
Why separate from OffByOne? OffByOneRepairStrategy targets the loop condition (root cause). BufferBoundsRepairStrategy guards the access point (symptom). They complement each other — OffByOne gets first priority because fixing the loop is better than guarding every access inside it.
Strategy 3

NullDereferenceRepairStrategy

The most sophisticated strategy — inserts null-safety guards for member accesses

Priority 3 NotNull(...)

When Does It Trigger?

Fires for NotNull(...) predicates — generated by Step 2 when a member access (like obj.Method()) is called on a value that was null at runtime.

The Core Challenge

Problem: Step 1's instrumenter catches exceptions at the method declaration line (e.g., line 10), not at the actual crashing statement (e.g., line 18). The strategy must scan the entire method body to find the real offender.

Two Execution Paths

Path A — Method-Level Violation

The violation line points to a method declaration (not a statement). The strategy:

  1. Collects method parameter names (these are usually not null)
  2. Scans each statement in the method body
  3. Finds member access expressions like obj.Something()
  4. Walks to the root receiver — the leftmost identifier
  5. Filters out parameters, type names, and literals
  6. Generates a null guard for the first matching local variable
Path B — Statement-Level Violation

The violation line points directly to a statement. The strategy:

  1. Finds all member access expressions in the statement
  2. Extracts receiver expressions
  3. Filters out literals and type names
  4. Wraps the statement in if (receiver is not null) { ... }

The Root Receiver Walker

The strategy needs to find what could be null in a chain like o.GetType().GetMethod("name"). It walks leftward through the expression tree to find the root:

// Expression chain:  method.Invoke(o, Array.Empty<object>())
//
// Walk: InvocationExpression → MemberAccess "method.Invoke"
//       → MemberAccess.Expression → IdentifierName "method"
//
// Result: "method" ← this is what could be null

The walker identifies method as the receiver, then checks: parameter? No → literal? No → type name? No (starts with lowercase) → Local variable → GUARD THIS

Example — Method-Level Scan (Path A)

Violation (at method declaration line)
"predicate": "NotNull(dereference.receiver)"
"file":      "MemberMethodResolver.cs"
"line":      10   // ← this is the method declaration, not the crash line
MemberMethodResolver.cs — null guard with scope-safe variable splitting
      MethodInfo method = o.GetType().GetMethod(
          methodInvoke,
          BindingFlags.Public | BindingFlags.NonPublic
          | BindingFlags.Instance | BindingFlags.Static
          | BindingFlags.DeclaredOnly)!;
-     bool shouldPersist = (bool)method.Invoke(o, Array.Empty<object>())!;
+     bool shouldPersist = false;
+     if (method is not null)
+     {
+         shouldPersist = (bool)method.Invoke(o, Array.Empty<object>())!;
+     }
      return shouldPersist;

Example — Direct Statement (Path B)

Service.cs — simple null guard around member access
      var name = user.Profile.GetDisplayName();
      var name = default;
      if (user.Profile is not null)
      {
          name = user.Profile.GetDisplayName();
      }

Scope-Safe Variable Declarations

Critical detail: When guarding a var x = obj.Method(); statement, naively wrapping it in if (...) { var x = ...; } would make x invisible to later statements. The strategy splits the declaration: first bool x = false; (safe default), then assigns inside the if-block.

int, long, double, etc.0Numeric zero

Receiver Filtering Rules

Not every expression in a member access can be null. The strategy filters out safe receivers:

Strategy 4

InvalidCastRepairStrategy

Replaces unsafe type casts with pattern-matched alternatives

Priority 4 ValidCast(...)

When Does It Trigger?

Fires for ValidCast(...) predicates — generated when Step 2 detects an InvalidCastException at runtime.

Three Sub-Strategies

Sub-Strategy 1 — Explicit Cast → is Pattern Match

Finds CastExpressionSyntax nodes like (int)obj and replaces them with a safe is pattern:

Before → After: explicit cast replacement
  var count = (int)obj;
  if (obj is int __castResult)
  {
      // AutoRepair: safe cast replacement for (int)obj
      var count = __castResult;
  }
How it works under the hood: The strategy uses Roslyn's ReplaceNode() to swap the CastExpressionSyntax with an IdentifierName("__castResult") inside the original statement — preserving everything else in the expression.
Sub-Strategy 2 — as Cast → Flag for Review

The as keyword already returns null on failure (instead of throwing), so the strategy adds a comment suggesting a null check:

Before → After: as cast flagged
  var item = obj as Product;
  // AutoRepair: added null check after 'as' cast to Product
  var item = obj as Product;
Sub-Strategy 3 — Generic Fallback

When the violation has type info in its bindings but no recognizable cast expression in the AST, adds an annotation for manual review.

Broader Example — Complex Expression

A cast inside a method call chain
  string name = ((Person)GetEntity(id)).Name;
  if (GetEntity(id) is Person __castResult)
  {
      // AutoRepair: safe cast replacement for (Person)GetEntity(id)
      string name = __castResult.Name;
  }
Strategy 5

IntegerOverflowRepairStrategy

Wraps arithmetic in checked blocks to catch silent overflow

Priority 5 NoOverflow(...)

The Problem

By default, C# arithmetic silently wraps around on overflow. int.MaxValue + 1 becomes int.MinValue — no exception, no error, just corrupted data. The checked keyword makes the runtime throw an OverflowException instead.

// Default (unchecked): silent corruption
int x = int.MaxValue;  // 2,147,483,647
x = x + 1;            // -2,147,483,648 (!!!) — no warning

// With checked: throws OverflowException
checked
{
    int x = int.MaxValue;
    x = x + 1;         // OverflowException — bug is now visible
}

When Does It Trigger?

Fires for NoOverflow(...) predicates, with additional metadata in the violation's bindings:

Binding KeyExample ValuePurpose
operator"+", "*"Which arithmetic operator overflowed
resultType"Int32", "Int64"The numeric type that wrapped around

Example — Simple Arithmetic

Calculator.cs — addition wrapped in checked block
      total = a + b;
      checked
      {
          total = a + b;
      }

Example — Compound Assignment

Accumulator.cs — compound operator wrapped
      runningTotal *= factor;
      checked
      {
          runningTotal *= factor;
      }

Example — Complex Expression

Matrix.cs — multi-operator expression
      result = (width * height) + padding;
      checked
      {
          result = (width * height) + padding;
      }
Why checked and not type promotion? The strategy could promote int to long, but that changes the type signature and can cascade changes throughout the codebase. checked { } is a non-invasive way to surface the bug — it preserves the original types and expressions while making overflow detectable.
Strategy 6

ExceptionRepairStrategy

The last-resort fallback — wraps code in try-catch with diagnostic logging

Priority 6 — Fallback NoUnhandledException(...)

When Does It Trigger?

Fires for NoUnhandledException(...) predicates — the catch-all for any runtime exception that wasn't matched by a more specific strategy. Every unhandled crash generates this predicate in Step 2.

Strategy Design

This is intentionally the least specific strategy. It doesn't try to understand the root cause — it just prevents the crash by wrapping the offending code in a try-catch block with diagnostic logging.

Features
  • Specific catch type — extracts the exception type from violation bindings (e.g., NullReferenceException). Falls back to Exception.
  • Diagnostic logging — adds Debug.WriteLine so the caught error is traceable.
  • Method body scanning — like NullDereferenceRepairStrategy, handles method-level violations.
Safety Checks
  • Double-wrap prevention — if the statement is already inside a try-catch, returns null (no patch).
  • Risky statement detection — only wraps statements that contain invocations on member accesses (potential throw points).

Example — Specific Exception Type

Violation with exception type from bindings
"predicate": "NoUnhandledException(event)"
"bindings":  { "event.exception.type": "System.NullReferenceException" }
"file":      "OrderService.cs"
"line":      25
OrderService.cs — try-catch with specific exception type
      result = service.Process(order);
      try
      {
          result = service.Process(order);
      }
      catch (NullReferenceException ex)
      {
          // AutoRepair: caught NullReferenceException at line 25
          System.Diagnostics.Debug.WriteLine(
              $"AutoRepair: {ex.GetType().Name} at OrderService.cs:25: {ex.Message}");
      }

Example — Method Body Scan

When the violation line points to a method declaration, the strategy scans forward:

Resolver.cs — first risky statement in method body gets wrapped
  public string Resolve(object input)
  {
      string key = input.ToString();  // ← skipped: already in try
      var result = cache.Lookup(key);  // ← first unprotected risky call
      try
      {
          var result = cache.Lookup(key);
      }
      catch (InvalidOperationException ex)
      {
          System.Diagnostics.Debug.WriteLine(...);
      }
      return result;
  }
When does this NOT fire? If a higher-priority strategy already produced a patch for the same line, the ExceptionRepairStrategy is never reached. For example, a NullReferenceException violation often comes paired with a NotNull violation — the NullDereferenceRepairStrategy (priority 3) handles it with a precise null guard, making the generic try-catch unnecessary.

Section 11

How Roslyn Analysis Works

Every strategy uses the same core Roslyn workflow: parse → locate → transform. Here's how it works under the hood.

Step 1 — Parse Source to AST

var tree = (CSharpSyntaxTree)CSharpSyntaxTree.ParseText(sourceCode, path: filePath);
var root = tree.GetRoot();  // the CompilationUnitSyntax — top of the tree

Roslyn turns your .cs file into a tree of syntax nodes. Every keyword, operator, brace, and identifier becomes a node with type information, line numbers, and parent/child relationships.

Step 2 — Find the Node at the Violation Line

All strategies use this pattern to locate the right AST node:

var node = root.DescendantNodes()
    .Where(n => n.GetLocation().GetLineSpan().StartLinePosition.Line + 1 == targetLine)
    .OrderByDescending(n => n.Span.Length)  // pick the WIDEST node at this line
    .FirstOrDefault();
Why widest? A single line can contain many nested nodes. For buffer[i] = i + 1;, the nodes include IdentifierName("buffer"), ElementAccessExpression, AssignmentExpression, etc. By picking the widest, we get the most complete context.

Step 3 — Walk to the Enclosing Statement

var statement = node.AncestorsAndSelf()
    .OfType<StatementSyntax>()
    .FirstOrDefault();

We walk up the tree to find the complete statement that contains the violation. This is what we'll replace in the source code.

Step 4 — Search for Specific Patterns

Each strategy then searches within the statement for its target pattern:

StrategySearches ForRoslyn Node Type
OffByOnei <= arr.LengthBinaryExpressionSyntax (LessThanOrEqual)
BufferBoundsarr[i]ElementAccessExpressionSyntax
NullDerefobj.Method()MemberAccessExpressionSyntax
InvalidCast(Type)exprCastExpressionSyntax
IntOverflowa + bBinaryExpressionSyntax (Add, Multiply, ...)
Exceptionobj.Call()InvocationExpressionSyntax

Step 5 — Generate the Patch String

Finally, the strategy builds the replacement code as a string, preserving the original indentation:

var indentation = GetIndentation(statement);  // e.g., "        " (8 spaces)

var patchedCode =
    $"{indentation}if ({condition})\n" +
    $"{indentation}{{\n" +
    $"{indentation}    {statement.ToString().Trim()}\n" +
    $"{indentation}}}";

return new PatchResult(..., OriginalCode: original, PatchedCode: patchedCode, ...);

Key Design Principles

Specificity First

Strategies are ordered from most specific to most generic. A precise loop fix (OffByOne) always wins over a generic try-catch (Exception).

First Success Wins

The engine stops at the first successful patch for each line. One patch per line, no conflicts.

AST-Driven, Not Text-Based

All strategies use Roslyn's parsed syntax tree — they understand code structure, not just text patterns.

Safe Defaults

Guards use safe defaults (false, 0, default). The patched code compiles and runs even when the original would crash.
