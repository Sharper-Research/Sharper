Section 1

High-Level Architecture

Step 3 is the final phase of the AutoRepair pipeline. It reads the violations discovered in Step 2, parses the original (un-instrumented) C# source code using Roslyn, locates the exact AST node at each violation line, dispatches the violation to a chain of repair strategies (ordered by specificity), and applies the first successful patch to the source file.

violations.json
From Step 2 — list of ConstraintViolation objects
↓
Original .cs source
.bak files from Step 1, or live files
↓
PatchEngine
Groups by file → de-duplicates by line → dispatches to strategies
↓
6 Repair Strategies (tried in priority order)
OffByOne → BufferBounds → NullDeref → InvalidCast → IntOverflow → Exception
↓
Patched source file + patches.json report
Key design principle: Strategies are ordered from most specific to least specific. OffByOneRepairStrategy only fires for OffByOne(...) predicates, while ExceptionRepairStrategy is the generic fallback that handles any NoUnhandledException(...). The engine tries each strategy in order and uses the first one that returns a non-null patch.

Section 3

Data Models

Three C# records define the data flowing through Step 3. All are immutable records with positional constructors.

ConstraintViolation (input)

Mirrors one entry from Step 2's violations.json. This is the input signal that tells the engine what is broken and where.

public sealed record ConstraintViolation(
    string  Predicate,   // "NotNull(dereference.receiver)" — which rule fired
    string  Assertion,   // human-readable assertion text
    Dictionary<string, object?> Bindings,  // rule-specific data (exception type, etc.)
    bool    Result,      // always false (a passed assertion wouldn't be a violation)
    string  File,        // "MemberMethodResolver.cs" — relative filename
    int     Line,        // 10 — source line number from the trace
    string  TraceId);    // GUID linking back to the exact trace event
The Predicate field is critical: it determines which strategy gets to handle this violation. Each strategy's CanHandle() checks whether the predicate starts with a specific prefix (e.g., "NotNull(" → NullDereferenceRepairStrategy).

PatchResult (per-patch output)

public sealed record PatchResult(
  string File,
  int    Line,
  string RuleName,
  string Description,
  string OriginalCode,
  string PatchedCode,
  ConstraintViolation Violation);

Contains both the original code snippet and its patched replacement — this is what gets string-replaced into the source file.

PatchReport (final output)

public sealed record PatchReport(
  string GeneratedAt,
  string ViolationsFile,
  string TargetRoot,
  int    TotalViolations,
  int    PatchesApplied,
  int    PatchesSkipped,
  List<PatchResult> Patches);

Serialized to patches.json — the full audit trail of what was changed and why.

Section 4

The Orchestrator Script — generate_patches.ps1

This PowerShell script is the user-facing entry point. It handles default paths, builds the project, and calls the compiled CLI with the right arguments.

Execution Flow

  1. Resolve paths — defaults to Step 2's violations.json and BrightHrKata as the target. These can be overridden via -ViolationsPath and -TargetSourceDir parameters.
  2. Validate inputs — checks that the violations file exists (Step 2 must have been run first).
  3. Build the Repair project — runs dotnet build Repair/Repair.csproj --nologo. Exits on failure.
  4. Call the CLI — runs dotnet run --project Repair.csproj --no-build -- --violations ... --target ... --report ....
    If the -Apply switch is set, adds --apply which writes patched code back to the source files. Otherwise, runs in dry-run mode (generates the report only).
  5. Report result — prints a summary and suggests re-running with -Apply if in dry-run mode.

Section 6

The Patch Engine — PatchEngine.cs

This is the heart of Step 3. The PatchEngine class orchestrates the entire workflow: reading violations, resolving source files, dispatching to strategies, and applying patches. Let's walk through every method.

Class Structure

public sealed class PatchEngine
{
    private readonly List<IRepairStrategy> _strategies;  // injected via constructor

    // Methods:
    //   RunAsync()           — main pipeline
    //   ReadViolationsAsync() — deserialize violations.json
    //   ResolveSourceFile()   — find original .cs/.bak file
    //   ApplyPatchesAsync()   — string-replace patches into source
}

Method 1: RunAsync() — The Main Pipeline

This is the method called by the CLI. Here it is broken down into its 5 phases:

Phase 1 — Read Violations

var violations = await ReadViolationsAsync(violationsPath);
// Deserializes violations.json → List<ConstraintViolation>
// For MicrosoftBugDemo: 2 violations loaded

Phase 2 — Group by File

var grouped = violations.GroupBy(v => v.File).ToList();
// Groups violations by their File field
// For MicrosoftBugDemo: 1 group ("MemberMethodResolver.cs" → 2 violations)

Phase 3 — Process Each File

foreach (var fileGroup in grouped)
{
    // 3a. Resolve the actual source file path
    var sourceFile = ResolveSourceFile(targetRoot, relativePath);
    // Checks: MemberMethodResolver.cs.bak → MemberMethodResolver.cs → filename search

    // 3b. Parse with Roslyn
    var sourceCode = await File.ReadAllTextAsync(sourceFile);
    var tree = (CSharpSyntaxTree)CSharpSyntaxTree.ParseText(sourceCode, path: sourceFile);
    // Now we have a full AST of the C# source file

    // 3c. De-duplicate by line
    var byLine = fileGroup.GroupBy(v => v.Line).OrderBy(g => g.Key);
    // For MicrosoftBugDemo: 1 group (line 10 → 2 violations)
    // Both violations point to line 10 because SafetyRewriter reports there
Why de-duplicate? Multiple violations can point to the same line. Without de-duplication, we'd generate conflicting patches for the same code. By grouping violations by line and taking only the first successful patch, we ensure each line is patched exactly once.

Phase 4 — Strategy Dispatch Loop

foreach (var lineGroup in byLine)
{
    PatchResult? patch = null;
    foreach (var violation in lineGroup)       // each violation at this line
    {
        foreach (var strategy in _strategies)   // in priority order
        {
            if (strategy.CanHandle(violation))      // predicate match?
            {
                patch = strategy.TryRepair(violation, sourceCode, tree);
                if (patch is not null) break;  // first success wins
            }
        }
        if (patch is not null) break;          // done with this line
    }
}
Double break pattern: The inner loop iterates strategies for a single violation. The outer loop iterates violations at the same line. As soon as any strategy returns a non-null patch for any violation at this line, both loops exit. This is why the 2nd violation at line 10 (NoUnhandledException) is never processed — the 1st violation (NotNull) already yielded a patch via NullDereferenceRepairStrategy.

Phase 5 — Apply Patches

if (applyPatches && filePatches.Count > 0)
{
    await ApplyPatchesAsync(sourceFile, sourceCode, filePatches);
}
// String-replaces each patch's OriginalCode with PatchedCode
// Patches are applied in reverse line order to preserve line numbers

Method 2: ResolveSourceFile() — Finding the Right Source

This method resolves a relative file name (from violations.json) to an absolute path. The resolution order is critical:

  1. Try .bak file first — targetRoot/MemberMethodResolver.cs.bak
    Step 1 backs up original files before instrumenting. The .bak is the clean, un-instrumented source — this is what we want to patch.
  2. Try live file — targetRoot/MemberMethodResolver.cs
    Falls back to the current file if no backup exists (e.g., when running Step 3 independently).
  3. Filename search — Directory.GetFiles(targetRoot, fileName, SearchOption.AllDirectories)
    If the relative path doesn't match the directory structure, search recursively by filename.
  4. Check candidates for .bak — among search results, prefer candidates that have a .bak version.
Why .bak first? After Step 1, the live .cs file is instrumented — full of TraceLogger.Log() calls. We need to patch the original code, not the instrumented version. Step 1's restore_project.ps1 restores from .bak, but Step 3 can also read the backup directly.

Method 3: ApplyPatchesAsync() — Writing Patches

private static async Task ApplyPatchesAsync(
    string filePath, string sourceCode, List<PatchResult> patches)
{
    // 1. Target the live .cs file, not the .bak
    var targetPath = filePath.EndsWith(".bak") ? filePath[..^4] : filePath;

    // 2. If live file doesn't exist, copy from .bak
    if (!File.Exists(targetPath) && filePath.EndsWith(".bak"))
        File.Copy(filePath, targetPath);

    var currentSource = await File.ReadAllTextAsync(targetPath);

    // 3. Apply patches in REVERSE line order
    foreach (var patch in patches.OrderByDescending(p => p.Line))
    {
        if (currentSource.Contains(patch.OriginalCode.Trim()))
        {
            currentSource = currentSource.Replace(
                patch.OriginalCode.Trim(),
                patch.PatchedCode.Trim());
        }
    }

    await File.WriteAllTextAsync(targetPath, currentSource);
}
Reverse-order application: Patches higher in the file don't shift the line numbers of code below them. By applying bottom-up, each patch's OriginalCode string is still present in the file when we try to replace it. This avoids the classic "cascading line offset" bug.
Section 7

The Strategy Interface — IRepairStrategy

public interface IRepairStrategy
{
    /// Returns true if this strategy can handle the given violation.
    bool CanHandle(ConstraintViolation violation);

    /// Attempts to produce a patched version of the source at the violation location.
    /// Returns the patch result, or null if no actionable repair can be derived.
    PatchResult? TryRepair(
        ConstraintViolation violation,
        string sourceCode,
        CSharpSyntaxTree tree);
}

Every strategy implements exactly two methods:

CanHandle() A fast predicate check — typically a StartsWith() on the violation's Predicate field. No Roslyn parsing happens here.
TryRepair() The heavy work — uses Roslyn to find the AST node at the violation line, determines if a repair is possible, and constructs the patched code string. Returns null if the strategy can't produce a valid fix.
Section 8

All 6 Repair Strategies — Code Analysis

Each strategy follows a common pattern: find node → analyze AST → generate patched string. But they differ significantly in what they look for and how they transform the code.

1. OffByOneRepairStrategy Priority 1

Trigger: violation.Predicate.StartsWith("OffByOne(")

Handles off-by-one errors where a loop iterates one element past the end of an array (e.g., i <= arr.Length instead of i < arr.Length).

Two Sub-Strategies

Strategy 1: Fix Loop Condition Searches for for/while loops enclosing the violation line. If the loop condition contains a <= comparison, rewrites it to <. This is the best fix because it addresses the root cause.

Roslyn approach: Finds BinaryExpressionSyntax with kind LessThanOrEqualExpression, replaces with {left} < {right}.
Strategy 2: Bounds Guard Fallback — wraps the violating statement in if (index >= 0 && index < arr.Length). Same approach as BufferBoundsRepairStrategy.

Example Transform

Loop condition fix
  for (int i = 0; i <= arr.Length; i++)
  for (int i = 0; i < arr.Length; i++)

2. BufferBoundsRepairStrategy Priority 2

Trigger: violation.Predicate.StartsWith("BufferInBounds(")

Handles array index-out-of-bounds access by inserting a bounds-check guard around the statement.

Algorithm

  1. Find node at line — Roslyn: find the deepest node at the violation line number
  2. Find enclosing statement — walk up the AST via .AncestorsAndSelf().OfType<StatementSyntax>()
  3. Find ElementAccessExpressionSyntax — these are arr[i] expressions
  4. Build guard — for each arr[i], generate i >= 0 && i < arr.Length
  5. Wrap statement — if (guards) { original statement }

Example Transform

Bounds guard insertion
  result = items[index];
  if (index >= 0 && index < items.Length)
  {
      result = items[index];
  }

3. NullDereferenceRepairStrategy Priority 3 — handles MicrosoftBugDemo

Trigger: violation.Predicate.StartsWith("NotNull(")

The most sophisticated strategy. Inserts null guards around member accesses on potentially-null local variables. Has special handling for method-level violations and variable scoping.

The Core Challenge

Step 1's SafetyRewriter wraps method bodies in try-catch and reports exceptions at the method declaration line (e.g., line 10), not at the actual crashing statement (e.g., line 18). The strategy must find the real offending statement by scanning the entire method body.

Algorithm — Two Paths

public PatchResult? TryRepair(violation, sourceCode, tree)
{
    var node = FindNodeAtLine(root, violation.Line);
    var statement = node.AncestorsAndSelf().OfType<StatementSyntax>().FirstOrDefault();

    if (statement is null)
    {
        // PATH A: Violation line is a method declaration → scan method body
        var method = node.AncestorsAndSelf().OfType<MethodDeclarationSyntax>()...;
        return RepairMethodBody(violation, method, targetLine);
    }

    // PATH B: Direct statement → repair it directly
    return RepairStatement(violation, statement, targetLine);
}

Path A: RepairMethodBody() — Method-Level Scanning

This is the path taken for the MicrosoftBugDemo (violation at line 10 = method declaration):

  1. Gather parameter names — {"o", "memberName"} from the method signature, used to filter out parameters as receivers.
  2. Iterate each statement in the method body, looking for MemberAccessExpressionSyntax nodes.
  3. Walk to root receiver via GetRootReceiver(): 
    // Walks leftward through the expression tree:
//   o.GetType().GetMethod(...)  →  o       (parameter — filtered out)
//   method.Invoke(...)          →  method  (local var — MATCH!)
//   Array.Empty<object>()       →  Array   (type name — filtered out)
  4. Filter receivers — skip parameters, type names (char.IsUpper(expr[0])), literals ("this", "base"), and namespaces.
  5. First match wins — the first statement with a non-filtered local variable receiver triggers the patch.

GetRootReceiver() — Expression Tree Walker

private static string? GetRootReceiver(ExpressionSyntax expr)
{
    while (true)
    {
        switch (expr)
        {
            case MemberAccessExpressionSyntax ma: expr = ma.Expression; continue;
            case InvocationExpressionSyntax inv:  expr = inv.Expression; continue;
            case IdentifierNameSyntax id:         return id.Identifier.Text;
            default:                              return expr.ToString();
        }
    }
}
// For: (bool)method.Invoke(o, Array.Empty<object>())!
//   → InvocationExpression → MemberAccess(method.Invoke)
//     → MemberAccess expression = "method"
//       → IdentifierName "method" → returns "method"

BuildNullGuard() — Scope-Safe Code Generation

The key innovation: when wrapping a LocalDeclarationStatementSyntax in an if-guard, the variable must remain visible to subsequent statements. The strategy splits the declaration:

LocalDeclarationStatementSyntax handling
// Original:
  bool shouldPersist = (bool)method.Invoke(o, Array.Empty<object>())!;

// What a naive guard would produce (BROKEN — shouldPersist out of scope):
  if (method is not null)
  {
      bool shouldPersist = (bool)method.Invoke(o, Array.Empty<object>())!;
  }
  return shouldPersist;  // ← ERROR: 'shouldPersist' does not exist here

// What BuildNullGuard actually produces (CORRECT):
  bool shouldPersist = false;          // declare with safe default
  if (method is not null)
  {
      shouldPersist = (bool)method.Invoke(o, Array.Empty<object>())!;
  }
  return shouldPersist;  // ← OK: shouldPersist is in scope
private static string BuildNullGuard(StatementSyntax stmt, string indent, string condition)
{
    if (stmt is LocalDeclarationStatementSyntax localDecl)
    {
        var typeName    = localDecl.Declaration.Type.ToString();      // "bool"
        var varName     = variable.Identifier.Text;                   // "shouldPersist"
        var initializer = variable.Initializer?.Value.ToString();      // "(bool)method.Invoke(...)!"
        var defaultVal  = typeName switch {
            "bool"  => "false",
            "int"   => "0",
            _       => "default"
        };

        return
            $"{indent}{typeName} {varName} = {defaultVal};\n" +    // bool shouldPersist = false;
            $"{indent}if ({condition})\n" +                         // if (method is not null)
            $"{indent}{{\n" +                                       // {
            $"{indent}    {varName} = {initializer};\n" +             //     shouldPersist = (bool)method...
            $"{indent}}}";                                            // }
    }

    // Non-declaration statements: just wrap directly
    return
        $"{indent}if ({condition})\n" +
        $"{indent}{{\n" +
        $"{indent}    {stmt.ToString().Trim()}\n" +
        $"{indent}}}";
}

4. InvalidCastRepairStrategy Priority 4

Trigger: violation.Predicate.StartsWith("ValidCast(")

Handles InvalidCastException by replacing unsafe direct casts with type-safe alternatives.

Three Sub-Strategies

1. Explicit Cast → is Pattern Finds CastExpressionSyntax like (TargetType)source. Replaces with a pattern match: if (source is TargetType __castResult) { ...use __castResult... }. Uses ReplaceNode() on the Roslyn AST to substitute the cast expression with the pattern variable.
2. as Cast → null check Finds BinaryExpressionSyntax with AsExpression kind. Flags it with a comment for manual review (the as pattern naturally returns null, so a guard may already exist).
3. Generic fallback If the violation has a target type in its bindings but no recognizable cast in the AST, adds an annotation comment.

Example Transform (Explicit Cast)

Direct cast → is pattern
  var count = (int)obj;
  if (obj is int __castResult)
  {
      var count = __castResult;
  }

5. IntegerOverflowRepairStrategy Priority 5

Trigger: violation.Predicate.StartsWith("NoOverflow(")

Handles integer overflow by wrapping arithmetic in checked { } blocks, which makes C# throw OverflowException instead of silently wrapping around.

Two Sub-Strategies

Int32 → promote/checked For Int32 overflow: finds BinaryExpressionSyntax with the specific operator (+, -, *, /) from the violation bindings.
Other types → checked block Wraps the entire statement in checked { ... }. Works for any numeric type.

Example Transform

Arithmetic → checked block
  total = a * b + c;
  checked
  {
      total = a * b + c;
  }

6. ExceptionRepairStrategy Priority 6 — Fallback

Trigger: violation.Predicate.StartsWith("NoUnhandledException(")

The generic last-resort strategy. Wraps the offending statement in a try-catch for the specific exception type reported in the violation's bindings.

Features

Specific exception type Extracts the exception type from violation.Bindings["event.exception.type"] (e.g., "System.NullReferenceException" → catches NullReferenceException). Falls back to Exception if not available.
Method body scanning Like NullDereferenceRepairStrategy, handles method-level violations by scanning the method body for statements with InvocationExpressionSyntax on member accesses.
Double-wrap prevention Checks statement.Ancestors().OfType<TryStatementSyntax>().Any() — if the statement is already inside a try-catch, returns null.

Example Transform

Statement → try-catch
  result = service.Process(input);
  try
  {
      result = service.Process(input);
  }
  catch (NullReferenceException ex)
  {
      System.Diagnostics.Debug.WriteLine($"AutoRepair: {ex.GetType().Name}...");
  }
