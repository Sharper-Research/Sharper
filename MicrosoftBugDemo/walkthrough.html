Section 1

Pipeline Overview

The AutoRepair system is a three-step pipeline that automatically finds bugs in C# programs and generates source-level patches to fix them — without any human intervention. Each step feeds its output into the next:

1

Tracing

Instrument source code with Roslyn rewriters, run tests, capture a detailed execution trace.

→
2

Constraints

Replay the trace through rule engines to detect safety violations (nulls, exceptions, overflows, etc.).

→
3

Repair

Parse the original source with Roslyn, match violations to AST nodes, generate & apply patches.

Key insight: The entire pipeline is fully automated. You give it a target source directory and a test project, and it instruments the code, runs the tests, analyzes the trace, and writes a patched file — all without any human guidance.

The Bug — What's Broken & Why

Real-World Origin

GitHub Issuedotnet/runtime#120561 (October 2025)
Original FileReflectionXmlSerializationWriter.cs in the .NET runtime
Bug TypeSystem.NullReferenceException
Root CauseBindingFlags.DeclaredOnly makes GetMethod() return null for methods defined on a base class

Simplified Reproduction

The MicrosoftBugDemo project distills the bug into a minimal, self-contained reproduction. Here is the buggy source file:

// MemberMethodResolver.cs — The buggy code
internal static class MemberMethodResolver
{
    public static bool CheckShouldPersist(object o, string memberName)
    {
        string methodInvoke = $"ShouldSerialize{memberName}";
        MethodInfo method = o.GetType().GetMethod(
            methodInvoke,
            BindingFlags.Public | BindingFlags.NonPublic
            | BindingFlags.Instance | BindingFlags.Static
            | BindingFlags.DeclaredOnly)!;      // ← DeclaredOnly skips base class!
        bool shouldPersist = (bool)method.Invoke(o, Array.Empty<object>())!;  // ← BOOM! method is null
        return shouldPersist;
    }
}
The problem: When memberName refers to a property defined on a base class (e.g., "BaseProp"), the flag BindingFlags.DeclaredOnly restricts the search to only methods declared directly on the derived class. Since ShouldSerializeBaseProp() is defined on TestBase (not Test), GetMethod() returns null. Calling .Invoke() on null throws a NullReferenceException.

The Test Suite

Three tests exercise this method with different scenarios:

// Test 1 — ✅ PASSES: method is on the same class (Test.ShouldSerializeTestProp)
var obj = new Test();
MemberMethodResolver.CheckShouldPersist(obj, "TestProp");
// GetMethod("ShouldSerializeTestProp") on Test → ✅ found (declared on Test itself)

// Test 2 — ✅ PASSES: method is on the same class (TestBase.ShouldSerializeBaseProp)
var obj = new TestBase();
MemberMethodResolver.CheckShouldPersist(obj, "BaseProp");
// GetMethod("ShouldSerializeBaseProp") on TestBase → ✅ found (declared on TestBase itself)

// Test 3 — ❌ FAILS: method is on the BASE class but called through the DERIVED class
var obj = new Test();
MemberMethodResolver.CheckShouldPersist(obj, "BaseProp");
// GetMethod("ShouldSerializeBaseProp") on Test with DeclaredOnly → ❌ null!
// method.Invoke() throws NullReferenceException

Section 4

Step 1 — Tracing (Instrumentation & Execution)

Step 1 is the data-collection phase. It modifies the target source code to emit structured trace events at runtime, runs the test suite, and captures every event into a JSONL log file.

1a. The PowerShell Script (generate_trace.ps1)

This script orchestrates the entire tracing phase:

Restore previous instrumentation

Calls restore_project.ps1 to revert any .bak files from earlier runs, ensuring we start with clean source.

Run the Instrumenter

Runs dotnet run --project Instrumenter with the target directory as argument. This modifies the .cs files in-place (after backing them up to .bak).

Execute the test suite

Runs dotnet test on the driver project with TRACE_LOG_JSON_PATH set as an environment variable. The instrumented code writes trace events to this file at runtime.

Stream trace events live

While tests execute, the script polls the JSONL file and prints new trace events to the console in real-time.

1b. The Instrumenter (Instrumenter/Program.cs)

The Instrumenter is a Roslyn-based C# program that parses each source file into a syntax tree, then applies six rewriters in a specific order. Each rewriter is a CSharpSyntaxRewriter that injects logging calls without changing program behavior.

Rewriter Pipeline (applied in order)

1. SafetyRewriter Wraps every method body in try-catch. The catch block logs the exception type, message, and stack trace. Also adds loop watchdogs and null-assignment detection. Must run first — the try-catch must wrap the entire method including code added by later rewriters.
2. ControlFlowRewriter Injects TraceLogger.Log() calls at method entry, if/else branches, loop iterations, switch cases, and return statements. Each log call includes a unique GUID, file name, and line number.
3. VariableRewriter Adds logging after every variable assignment (x = 5), compound assignment (x += 1), and increment/decrement (i++). Captures the variable's name and value.
4. HeapRewriter Logs array allocations, array snapshots, and parameter-to-argument aliases for array tracking.
5. CastingRewriter Wraps explicit casts and as casts to log source/target types, detecting InvalidCastException.
6. OverflowRewriter Wraps arithmetic binary operations in checked contexts to detect integer overflow.

1c. What the Instrumented Code Looks Like

After 6 rewriters process MemberMethodResolver.cs, the original 7-line method becomes heavily instrumented: 

public static bool CheckShouldPersist(object o, string memberName)
{
  TraceLogger.Log(..., "Enter Method 'CheckShouldPersist'");
  try                                              // ← SafetyRewriter
  {
      string methodInvoke = ...;
      TraceLogger.Log(..., "Variable Update", methodInvoke, "methodInvoke");

      MethodInfo method = o.GetType().GetMethod(...);
      TraceLogger.Log(..., "Variable Update", method, "method");   // ← captures null!

      bool shouldPersist = (bool)method.Invoke(...);       // ← crash here
      TraceLogger.Log(..., "Variable Update", shouldPersist, "shouldPersist");

      TraceLogger.Log(..., "Return");
      return shouldPersist;
  }
  catch (Exception ex)                               // ← SafetyRewriter
  {
      TraceLogger.Log(..., "Exception Caught", ex.Message, "ex.Message");
      if (ex is NullReferenceException)
          TraceLogger.Log(..., "Null Dereference", ex.Message, "null.dereference");
      TraceLogger.Log(..., "Exception Type", ex.GetType().FullName, "ex.Type");
      TraceLogger.Log(..., "Exception Stack", ex.StackTrace, "ex.Stack");
      throw;
  }
}
Important detail: The SafetyRewriter logs the exception at the method declaration line (line 10), not at the actual crashing statement (line 18). This is because the try-catch wraps the entire method body. This line-number mismatch is a key challenge that Step 3 must handle.

1d. The Generated TraceLogger

The Instrumenter also generates a TraceLogger.cs file inside the target project. This static class writes structured JSON events to a file. Each event contains:

Section 5

Step 2 — Constraint Analysis (Violation Detection)

Step 2 replays the trace file through a set of rule engines. Each rule looks for specific trace event patterns that indicate a safety violation. The rules are stateless assertions: they don't know about the source code — only the trace events.

2a. How It Works

Input: trace_logs.jsonl (18 events)
↓
TraceReader — parses JSONL into TraceEvent objects
↓
StateTracker — maintains running state (variables, buffers, aliases)
↓
6 Rules — each evaluates every event for violations
NullDereferenceRule · ExceptionRule · BufferBoundsRule · OffByOneRule · InvalidCastingRule · IntegerOverflowRule
↓
Output: violations.json (2 violations)

2b. Rules That Fire

Rule 1: NullDereferenceRule

When it sees event #16 (msg: "Null Dereference"), it fires:

{
  "predicate": "NotNull(dereference.receiver)",
  "assertion": "dereference receiver is not null",
  "bindings": {
    "signal": "Null Dereference",
    "exception.message": "Object reference not set to an instance of an object."
  },
  "result": false,
  "file": "MemberMethodResolver.cs",
  "line": 10               // ← method declaration line (from SafetyRewriter)
}
Note: The NullDereferenceRule also suppresses the next "Exception Type" event for NullReferenceException to avoid a duplicate violation. This is why we get 2 violations instead of 3.

Rule 2: ExceptionRule

When it sees event #17 (msg: "Exception Type"), it fires:

{
  "predicate": "NoUnhandledException(event)",
  "assertion": "event.exception == null",
  "bindings": {
    "event.exception.type": "System.NullReferenceException"
  },
  "result": false,
  "file": "MemberMethodResolver.cs",
  "line": 10
}

2c. Rules That Don't Fire (and why)

BufferBoundsRuleNo array index-out-of-range events in the trace. This code doesn't use indexed access.
OffByOneRuleNo buffer access patterns to analyze. This bug is a null dereference, not an off-by-one error.
InvalidCastingRuleNo "Invalid Cast" events. The (bool) cast on line 18 never executes because the NullReferenceException happens first on method.Invoke().
IntegerOverflowRuleNo arithmetic operations in this code.
Section 6

Step 3 — Repair (Patch Generation & Application)

Step 3 reads the violations from Step 2, parses the original (un-instrumented) source code using Roslyn, and attempts to generate source-level patches that fix each violation.

3a. The Patch Engine Pipeline

Input: violations.json + original source (.bak files)
↓
PatchEngine — reads violations, groups by file, resolves source paths
↓
Roslyn Parse — parses the original .cs file into a CSharpSyntaxTree
↓
Strategy Dispatch — tries strategies in priority order until one generates a patch
OffByOne → BufferBounds → NullDeref → InvalidCast → IntOverflow → Exception
↓
De-duplicate — groups violations by line, uses first successful patch per line
↓
Apply — string-replace original code with patched code, write to file

3b. The Key Challenge: Line Number Mismatch

Both violations point to line 10 — the method declaration — because that's where the SafetyRewriter's catch block reports exceptions. But the actual null dereference happens at line 18 (method.Invoke(...)).

The NullDereferenceRepairStrategy handles this elegantly:

1. Find node at violation line (line 10)

Roslyn finds a MethodDeclarationSyntax at line 10 — not a statement.

2. Direct StatementSyntax lookup → null

node.AncestorsAndSelf().OfType<StatementSyntax>() returns nothing because a method declaration is not a statement.

3. Fall back to method body scan

Recognizes this is a MethodDeclarationSyntax, enters RepairMethodBody().

4. Iterate method statements, filter receivers

For each statement, finds MemberAccessExpressionSyntax nodes, walks leftward to find root receivers, filters out:

  • Parameters (o, memberName) — unlikely to be null
  • Type names (Array, BindingFlags) — static, can't be null
  • Literals ("this", "base")

5. Statement 1: string methodInvoke = ...

Root receiver of $"ShouldSerialize{memberName}" is a string interpolation — no member access. Skipped.

6. Statement 2: MethodInfo method = o.GetType().GetMethod(...

Root receiver is o — which is a parameter. Filtered out.

7. Statement 3: bool shouldPersist = (bool)method.Invoke(...)

Root receiver is method — a local variable, not a parameter, not a type name. Match!

8. Generate null guard with scope-safe variable handling

Since this is a LocalDeclarationStatementSyntax, the strategy uses BuildNullGuard() to declare the variable with a default value before the guard, so it remains in scope for the return statement on the next line.

3c. Why Only 1 Patch (Not 2)?

Both violations point to the same line (10). The PatchEngine groups violations by line and uses the first successful patch. Since the NullDereferenceRepairStrategy (priority 3) handles the NotNull(...) violation successfully, the second NoUnhandledException(...) violation at the same line is covered by the same patch. Result: 1 patch generated, 0 skipped.

  3. If method is null (base class method not found), the method now returns false instead of crashing.

Final Result — The Patched Code

    MethodInfo method = o.GetType().GetMethod(
        methodInvoke,
        BindingFlags.Public | BindingFlags.NonPublic
        | BindingFlags.Instance | BindingFlags.Static

    return shouldPersist;
}

After (patched by AutoRepair)

public static bool CheckShouldPersist(object o, string memberName)
{
    string methodInvoke = $"ShouldSerialize{memberName}";
    MethodInfo method = o.GetType().GetMethod(
        methodInvoke,
        BindingFlags.Public | BindingFlags.NonPublic
        | BindingFlags.Instance | BindingFlags.Static
        | BindingFlags.DeclaredOnly)!;
    bool shouldPersist = false;
    if (method is not null)
    {
        shouldPersist = (bool)method.Invoke(o, Array.Empty<object>())!;
    }
    return shouldPersist;
}
